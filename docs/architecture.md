# 저장과 정리 작업의 경계

메인 Flutter 엔진이 DB와 열린 창의 상태를 소유합니다. 개별 창은 IPC로 작업을
요청합니다. 데이터베이스 파일을 각 창에서 따로 수정하지 않습니다.

- `MainController`: 창·IPC·화면 갱신을 연결합니다. 테스트에는 DB를 주입할 수 있습니다.
- `NoteSaveService`: 저장 요청을 직렬화합니다. DB에서 성공한 변경만 메모리 상태로
  전달합니다. 메타데이터 변경은 실행 시점의 최신 메모에 적용합니다.
- `GroupService`: 묶음 생성·이동·빼기·이름 변경·삭제와 실행 취소를 소유합니다.
  가져오기용 묶음 생성도 이 서비스에서 처리합니다.
- `AppDatabase`: 조건부 메모 수정과 묶음 트랜잭션을 수행합니다.
  일반 편집은 활성 행만 UPDATE하므로 늦은 저장이 삭제된 메모를 복원하지 않습니다.
  새 메모 생성·가져오기에서만 명시적으로 upsert를 사용합니다.

## 실행 취소와 동시 변경

화면은 이전 소속을 직접 보내지 않고, 메인에서 발급받은 불투명한 작업 토큰을
보냅니다. 서비스는 영향을 받은 메모와 묶음의 변경 번호를 확인합니다. 다른 창에서
변경한 뒤 같은 값으로 돌아왔더라도 변경 번호가 달라지므로 오래된 취소를 거절합니다.
일괄 취소는 하나라도 충돌하면 전부 거절합니다. 관계없는 메모의 작업은 취소를
막지 않습니다. 새 묶음에 나중에 다른 메모가 추가됐다면 생성 취소 시 그 묶음은 남깁니다.

토큰은 메인 프로세스에 최근 100개까지만 보관하며 재시작하면 사라집니다.
변경 번호 역시 같은 DB 소유자의 세션 안에서만 유지하므로 DB 스키마 변경이 필요하지
않습니다. 묶음 트랜잭션 실패 시 SQL 변경과 변경 번호를 함께 되돌려 안전하게
재시도할 수 있습니다. 이 보장은 현재의 단일 DB 소유자 구조를 전제로 합니다.
별도 프로세스나 동기화 기능이 DB를 수정하게 된다면 변경 번호도 DB에 영속화해야 합니다.

IPC 계층은 플러그인의 `WindowChannelException`을 작업 충돌 오류로 변환합니다.
UI는 충돌이면 현재 상태를 유지한다고 알리고, 저장 오류에는 재시도를 제공합니다.
현재 `GroupService`의 충돌 검사는 묶음 작업에 적용됩니다. 참고 연결은 별도 경로입니다.

## 검증과 남은 범위

`note_save_service_test.dart`는 저장 실패 후 재시도, 저장 중 메타데이터 변경,
삭제된 메모의 늦은 저장을 검사합니다. `group_service_test.dart`는 여러 창의 후속
변경, 같은 값으로 복귀하는 변경, 일괄 취소의 원자성, 생성·삭제 취소, DB 오류 후
재시도를 검사합니다. 위젯 테스트는 실제 IPC 래퍼를 거쳐 실패·충돌 안내를 확인합니다.

MainController에는 아직 모델 관리·가져오기·백업·창 관리 조정이 남아 있습니다.
모든 기능을 계층화한 구조는 아니며, 해당 기능이 복잡해질 때 경계를 추가로 분리합니다.
